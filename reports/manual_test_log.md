## 记录规则

- 真实测试通过后再把结果改为“通过”。
- 出现异常时填写异常说明，并保留对应提交号或模块版本。
- 大改后至少复测 Spotify、YouTube、知乎、登录、支付、验证码。
- 涉及 MITM、Body Rewrite、Map Local 或大型 JSON 改动后，必须重新测试高风险 App。
- Stable Plus 测试通过不等于自动进入 Stable；只能进入可晋级候选报告。

## 测试步骤模板

### 通用前置步骤

1. 在 Shadowrocket 中只启用一个版本。
2. 更新模块、更新脚本、更新全部资源。
3. 确认模块版本日期与模块顶部 `#!desc` 一致。
4. 开启日志，记录异常 App、触发时间、网络环境、模块版本和最近 commit。
5. 测试前后分别截图保留关键页面，异常时不要直接写“通过”。

### Stable 测试重点

1. Spotify：连续播放、切歌、搜索、歌单加载。
2. YouTube：首页、搜索、播放、Shorts、评论区。
3. 知乎：首页、回答页、搜索、评论、点赞、收藏。
4. Bilibili：首页、搜索、播放页、评论区。
5. 淘宝 / 京东 / 拼多多：首页、搜索、商品详情、购物车、订单页。
6. 美团 / 大众点评 / 饿了么：首页、搜索、店铺页、下单前置页。
7. 微信 / 支付宝 / 银行 App：登录、验证码、支付前置流程、消息推送。

### Stable Plus 测试重点

1. 只在 Stable 核心流程无异常后测试。
2. 逐类测试，不要一次性宣称全部通过。
3. 每个 App 至少测试首页、搜索、详情页、登录状态和广告残留。
4. 涉及订单、支付、验证码的 App 只测试前置流程，不进行真实大额付款。
5. 任一异常都不能晋级 Stable。

## 判定标准

- “通过”：核心流程无异常，且没有明显误杀。
- “部分通过”：核心流程可用，但有广告残留或局部异常。
- “失败”：登录、播放、支付前置、验证码、订单等核心流程异常。
- “未测试”：没有真实手动操作，不得改成通过。
