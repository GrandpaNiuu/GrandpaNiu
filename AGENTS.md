GrandpaNiu AI Maintenance Rules

This repository contains Shadowrocket / Surge / Android / Windows routing rules and advertising cleanup modules. It is high risk because a small rule mistake can break login, payment, media playback, image/CDN loading, or normal app networking.

Every AI assistant or maintainer must treat the repository records as the source of truth. Do not rely only on chat history.

Required Startup Reading

Before starting any work, read these files first if they exist:

* PROJECT_STATE.md
* AI_HANDOFF.md
* docs/ai/TASKS.md
* docs/ai/DECISIONS.md
* docs/ai/RISK_LOG.md
* Recent entries in docs/ai/WORKLOG.md

If any required record file is missing, create or repair the maintenance record first. Do not touch business logic, routing rules, scripts, workflows, release outputs, or generated files until the maintenance records exist.

Required Pre-Change Checks

Before every modification, run:

git status
git branch --show-current

If there are uncommitted changes, explain them first. Do not overwrite, delete, normalize, reformat, or silently modify user changes.

Safety Rules

1. No unrelated refactors.
2. No broad formatting of unrelated files.
3. Do not run dangerous commands without explicit user confirmation:
    * git reset --hard
    * git clean -fd
    * Force-overwriting many files
    * Deleting core directories
    * Deleting Release, Rules, Rewrite, Scripts, Android, Windows/v2rayN, or other key directories
    * Changing public module entry points
    * Changing repository version strategy
4. The repository currently prioritizes one public iOS entry: the Fusion module. Do not casually reintroduce Stable, Lite, Full, Aggressive, or other public multi-version routes.
5. Do not casually change public entries:
    * Ronghemokuai.sgmodule
    * Release/Module.sgmodule
    * Release/Ronghemokuai.sgmodule
6. Before changing rules, identify the source layer:
    * Rules
    * Rewrite
    * Scripts
    * Android
    * Windows/v2rayN
    * Release
    * tools
    * GitHub Actions workflows
7. Do not directly edit generated outputs unless you have confirmed the file is not generated by the build system.
8. Treat login, payment, banking, captcha, video playback, image/CDN paths, account systems, and normal app networking as protected high-risk traffic. Write a risk note before changing them.
9. Do not add VIP unlock, paid membership unlock, payment bypass, login bypass, receipt forgery, piracy enablement, credential theft, account-sharing bypass, or traffic interception logic.
10. Prefer source-first changes under:

* Rules/
* Rewrite/Sources/
* Rewrite/Remotes/
* Scripts/
* Android/
* Windows/v2rayN/
* tools/

11. Keep changes narrow. Modify only the files directly related to the current task.
12. If a requested change may break protected traffic or public module compatibility, stop and explain the risk before editing.

Required Finish Checks

After each change, run:

git diff --stat
git diff

Run the narrowest relevant checks first. When touching build logic, rules, scripts, workflows, or generated release outputs, prefer:

python Rewrite/Generator/Builder.py --profile fusion --release --check
python scripts/quality_gate.py
python scripts/validate_repository.py
python scripts/repository_health_check.py

If a check cannot be run, explain why and record the limitation in the work log.

Required Record Updates

Before finishing every task, update these records:

* PROJECT_STATE.md
* AI_HANDOFF.md
* docs/ai/WORKLOG.md
* docs/ai/TASKS.md

Update these when relevant:

* docs/ai/DECISIONS.md
* docs/ai/RISK_LOG.md

The work log entry must include:

* Task summary
* Starting branch and git status summary
* Files changed
* Reason for each change
* Commands run
* Test or validation result
* Risks
* Next step

Local Private Logs

Private working notes live outside the repository at:

../_codex_private_logs/GrandpaNiu/

Do not commit that directory.

Private logs may contain command notes, debugging details, local paths, longer work logs, and temporary investigation notes.

If _codex_private_logs is found inside the repository, do not commit it. Report it to the user and ask whether it should be moved outside the repository.

Git Commit Rule

Do not create a Git commit unless the user explicitly asks for it.

When suggesting a commit message, use this format:

codex: short description of the completed change

Final Response Requirement

At the end of each task, report:

1. What was changed
2. Which files were changed
3. What checks were run
4. Whether the repository has uncommitted changes
5. What risks remain
6. What should be done next
