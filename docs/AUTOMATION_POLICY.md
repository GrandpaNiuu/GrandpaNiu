# 自动化维护策略

本仓库目标是专业化、长期稳定、可自动维护的模块工厂，但自动化必须有边界。自动化的重点是收集、筛选、构建、验证、报告和告警；默认 Stable 不接受未知内容无审核直入。

## 维护原则

- 所有已纳入覆盖的 App 一视同仁维护，不设置单独例外。
- 所有 App 的登录、支付、验证码、银行、账户权益、Cookie、Token 都按高风险处理。
- 不因为某个 App 长期使用就降低安全门槛。
- 不因为某个 App 新加入就提高或降低维护待遇。
- 功能覆盖要完整，但稳定性优先于盲目堆规则。

## 自动化可以做到什么

仓库可以自动执行：

1. 构建 Stable / Stable Plus / Lite / Full 四个独立模块。
2. 同步 Root 与 Release。
3. 检查 profile 是否能构建。
4. 检查 Root / Release 一致性。
5. 检查 Python 脚本语法。
6. 检查 `Scripts/app-cleaner.js` JavaScript 语法。
7. 扫描脚本清单、重复入口和可融合候选。
8. 生成 App 覆盖矩阵。
9. 生成 Stable Plus 晋级候选报告。
10. 生成仓库健康报告。
11. 收集可信候选规则源。
12. 对 workflow 失败自动创建 Issue。

## 自动化不应直接做到什么

以下内容不能无审核自动进入 Stable：

- 未知作者脚本。
- 混淆脚本。
- 会员权益、破解、绕过类脚本。
- 登录、支付、验证码、银行、账户状态相关脚本。
- Cookie、Token、BoxJS、持久化账户状态依赖。
- 会修改 request body 的复杂脚本。
- 无法解释用途的远程模块。
- 没有回滚路径的大规模 MITM 增加。

## 安全自动拉取流程

正确流程：

```text
可信来源收集
-> 静态安全扫描
-> 生成候选报告
-> 放入 pending 或 Stable Plus
-> 构建验证
-> 语法验证
-> 重复检查
-> 人工真机测试
-> 单项晋级 Stable
```

## 候选源进入规则

可以作为候选的内容：

- 明确用于广告、开屏、弹窗、推荐位、统计接口清理的规则。
- 来源稳定、结构清楚、URL 可读的规则或脚本。
- 不涉及账户状态、支付、验证码、会员权益的普通净化逻辑。
- 能通过语法检查和构建检查。

必须阻断的内容：

- 破解、会员、Premium、解锁、绕过、伪造权益。
- Cookie、Token、BoxJS、登录态、账户态。
- 支付、验证码、银行、安全验证。
- 成人、博彩、短链、镜像、ghproxy、混淆脚本。
- 无法解释用途或无回滚路径的大量 hostname。

## 自动晋级策略

- 规则源可以自动进入候选报告。
- 低风险规则可以进入 Stable Plus 或 pending。
- Stable Plus 不自动整体合并到 Stable。
- Full 不自动整体合并到 Stable。
- 晋级 Stable 必须单项、可回滚、可解释。

## 专业度判断

当前仓库已经具备专业模块工厂的主要结构：

- 多版本发布。
- Profile 分层。
- Root / Release 一致性检查。
- 脚本融合与回滚报告。
- Workflow 失败自动开 Issue。
- 健康报告和覆盖矩阵。
- 自动候选源收集。
- 自动构建和验证。

但它不能被称为完全无人值守，因为真机 App 行为无法由 GitHub Actions 自动确认。专业结论应该是：

```text
专业化自动维护仓库：是
完全无人值守自动验证所有 App：否
默认 Stable 无审核自动吸收外部脚本：不应该
```

## 后续方向

1. 继续完善候选源安全评分。
2. 对候选脚本增加关键词扫描和混淆检测。
3. 对低风险规则建立自动 pending 区。
4. 对 Stable Plus 测试通过的单项 App 生成晋级 PR。
5. 对所有晋级保留回滚报告。
6. 继续降低脚本入口数量，但不牺牲功能和稳定性。
